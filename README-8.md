**作者：基隆私立二信高中｜普通科數理班｜P2C29 張博程**  
**作品類型：高中自主學習／資訊與藥學跨領域探索**  
**作品網址：** https://posen8745-cell.github.io/santong-drug-search/  
**GitHub 原始碼：** https://github.com/posen8745-cell/santong-drug-search

> **作品定位**：這是一套協助**查詢藥品資料、整理可能的三同候選品項**的教育與資訊工具。它不提供藥局或供應商的即時庫存、不保證藥品有貨，也不會自動判定處方能否替代。實際調劑、給付與替代用藥，仍須由藥師依處方、現行規定及必要的醫師確認辦理。

## 一、作品介紹與自主學習動機

### 為什麼想做這個工具？

這項作品的起點，來自爸爸工作上遇到的實際困難。爸爸在處理**慢性病連續處方箋**時，有時會受到**藥品缺貨或供應不穩定**的困擾。處方上寫的藥品如果一時無法取得，就需要花時間確認藥品資訊，以及是否存在可供專業人員進一步評估的其他廠牌品項。

我看到這個問題後，開始思考：**能不能把原本分散的藥品資料整理在一個網站，讓查找更快速、條件更清楚？** 我已經學過 Python 的資料處理，也有製作網頁工具的經驗，因此想嘗試做一套可以用藥名、健保碼或成分查詢的系統，把「同成分、同含量、同劑型」的概念轉換成程式篩選條件。

但我也逐漸了解到，**找到名稱或規格相似的藥，不等於確認可以替代，更不代表藥局現在買得到**。所以這個作品的功能定位，是先整理可供核對的藥品資訊，讓專業人員進一步確認，而不是讓程式直接決定病人用藥。

### 從生活問題到網頁作品

我先研究公開藥品資料的欄位，再嘗試處理中文編碼、日期、成分與價格資料，最後把查詢功能製作成可透過 GitHub Pages 開啟的網站。比起單純完成一道程式題目，這項作品讓我練習如何面對**資料來源不一致、欄位缺漏，以及使用結果可能被誤解**的問題。

## 二、自主學習目標

1. **理解問題**：觀察慢箋調劑時，缺藥會帶來哪些資料查找與核對需求。
2. **整理資料**：認識健保碼、品名、成分、含量、劑型、給付期間、支付價等欄位的差異。
3. **實作搜尋**：以網頁提供中文、英文、健保碼、成分及廠商等條件查詢。
4. **練習比對**：在資料足夠可靠的品項中，用程式列出符合嚴格條件的三同**候選清單**。
5. **重視正確性**：處理亂碼與缺漏資料，記錄來源、校正依據及需要人工查核的項目。
6. **清楚表達限制**：區分「有資料可查」「符合候選條件」「可以調劑替代」「真的有貨」等不同概念。

## 四、「三同」比對的概念與程式界線

我研究的「三同」主要是：

- **同成分**：不能只看藥名相似，還要核對實際的有效成分及必要的成分細節。
- **同含量／劑量**：含量與給藥規格必須核對；不能只看到相同數字就認定一致。
- **同劑型**：例如錠劑、膠囊等，並注意緩釋、腸溶等特殊釋放型態可能影響判斷。

本系統採取保守的比對策略。程式會正規化部分文字格式，檢查完整成分集合、各成分含量、詳細劑型與給藥規格；再加上官方分類分組等限制。不足以可靠比對的複方、非口服固體、疑似特殊釋放型態、欄位不完整或編碼異常品項，仍可搜尋，但**不自動列入三同候選清單**。

**重要區別：候選結果 ≠ 法規或臨床上已可替代。** 實際上仍需要核對處方是否註明不得替代、適應症、使用方式、給付規定、價格要求、藥品許可證及專業判斷，並依規定告知病人或聯繫原處方醫師。這些不是本工具目前能完全自動完成的工作。

## 五、資料來源與數字代表什麼

### 已整合的資料

依原專案文件，本版匯入健保署**115 年 11 月查詢檔（另案上網）**；原始歷次紀錄共 **225,028 筆**，彙整為 **45,224 個健保碼**。以 **2026-10-30** 作為程式資料快照日，其中符合「快照日有正支付價且給付期間涵蓋該日」條件者為 **13,838 個健保碼**。

這些數字代表**資料筆數及程式篩選結果**，**不代表有多少種藥可買到、不代表任何藥局的庫存量，也不代表當日可調劑的品項數**。快照日期也不是官方文件的發布日期；本版的 `updatedAt` 維持 `null`，避免誤稱已確認官方發布時間。

### 為什麼需要查核中文名稱？

在匯整過程中，我發現部分中文品名有問號或無法正確解碼的字元。專案原有紀錄顯示，以 **2026-10-30** 的食藥署許可證資料進行交叉核對時，涉及 **422 個健保碼**；其中 **415 個**有足夠依據修正，**7 個**仍標示為待核對。

這讓我體會到：即使資料來自公開來源，也可能因編碼、格式或版本不同而產生問題，不能為了讓網頁看起來完整，就自行猜測藥品名稱或成分。

## 六、網站操作與示範流程

1. 開啟 [三同・藥品查詢網站](https://posen8745-cell.github.io/santong-drug-search/)。
2. 使用**中文／英文藥名、健保碼、成分或廠商**等已支援的條件搜尋。
3. 檢視搜尋結果的藥品資料、成分、含量、劑型及給付期間等欄位。
4. 對符合程式範圍的品項，查看三同**候選**結果；若沒有候選，不代表醫療上完全沒有其他處理方法。
5. 需要整理資料時，可使用 CSV 匯出；若要匯入自備資料，需先確認資料格式與內容經過核對。
6. **若遇到真正的缺藥個案**，應再由藥師確認實際庫存、供貨狀況及法規／臨床適用條件；不得只根據網頁結果調換用藥。

**示範時建議使用公開藥品資料，不輸入病人姓名、身分證字號、處方照片或其他個資。**

## 八、自主學習過程與收穫

### 1. 從「搜尋藥名」到「設計可核對的篩選條件」

原本我以為，只要藥名相近，查詢就能幫上忙。整理資料後才發現：藥名、成分、含量、劑型、給藥規格與給付期間都可能影響結果。真正困難的地方，不只是把資料顯示出來，而是**哪些條件不足時，程式就不應自行做結論**。

### 2. 理解資料清理與驗證的重要

中文名稱亂碼、不同來源的資料欄位，以及快照日期與官方發布日期的差異，都讓我學會留下可追溯的證據，而不是只修改畫面上的文字。這也讓我認識到資料工程和一般程式練習的不同。

### 3. 體會資訊工具與專業判斷的分工

這個工具能協助找出需要進一步檢查的候選資料，但不能判斷庫存、實際臨床適用性或是否可以替病人換藥。我希望作品能幫忙減少重複查找的時間，同時把必須由藥師判斷的部分清楚標示。

### 4. 與未來科系探索的連結

- **資訊工程**：資料解析、條件比對、網站前端、資料庫、測試與版本管理。
- **藥學**：藥品成分、含量、劑型、調劑安全與專業審核的重要性。
- **電機／資訊整合**：這次主要是軟體與資料系統，並**沒有硬體或感測器實作**；若未來研究設備端資料傳輸、藥局資訊系統整合，才有更直接的延伸方向。

## 九、目前限制與未來研究

**目前限制**

- 這不是藥局庫存系統，**沒有即時缺藥、訂貨、供貨或庫存資訊**。
- 篩選名單不是調劑指示；不能只因顯示「三同候選」就自行改藥。
- 並非所有品項都開放自動三同比對；複方與特殊劑型等可能只提供搜尋。
- 藥品資料為特定快照及價格期間資料，不會自動更新成最新官方資料。
- 若主檔含漏填、錯誤或未及時更新，搜尋與比對結果也會受影響。
- 本網站不含病人處方、健保雲端病歷或個人醫療資料。

**未來可研究的方向（尚未完成）**

1. 設計可清楚顯示資料來源日期、版本及比對限制的介面。
2. 建立更容易操作的人工查核紀錄，讓專業人員知道候選品項還缺哪些核對資訊。
3. 研究正式且合法的供貨／短缺公開資訊來源與更新機制，先區分「公開通報」和「單一藥局即時庫存」。
4. 在具備專業審核的前提下，逐步研究其他劑型、複方與特殊釋放型態資料如何表示，但不直接自動宣稱可替代。
5. 以不含個資的測試情境，檢查搜尋速度、錯誤提示及使用者能否理解比對結果。

### 正式資料庫

已載入使用者提供的健保署「115年11月查詢檔（另案上網）」TXT ZIP。225,028 筆原始歷次紀錄，45,224 個健保碼，2026-10-30 快照日有正支付價且期間涵蓋當日者為 13,838 個健保碼。這不是供貨或庫存數量。

網站頁尾提供 SQLite GZIP 下載。部署時由 JSON 分檔產生 SQLite（drugs、ingredients、price_periods、metadata 四表，另有 name_audit 查核紀錄表），有健保碼、名稱、價格日期索引。下載後解壓縮即可用 SQLite 工具開啟。不含病人或處方資料。GitHub Pages 前端讀取壓縮 JSON，無須後端；需要支援 DecompressionStream 的瀏覽器。

重新匯入官方 TXT：`python3 scripts/build_nhi.py RAW_DIRECTORY --as-of YYYY-MM-DD`。程式按 1,859 位元組 Big5 格式解析，遇到長度／日期／數值異常就停止，無法解碼字元保留替換符且停用該品項比對。SQLite 重建：`python3 scripts/build_sqlite.py`。更新資料後先執行 `npm test` 再提交全部資料分檔與清單。不會自動抓取官方資料。

### 中文名稱查核修正

2026-10-30 以食藥署「全部藥品許可證資料集」72,096 筆許可證紀錄交叉核對。中文名稱含問號或替換字元者共有 422 個健保碼，其中 415 個確認並修正，7 個未能可靠確認而保留原名、標示待核對。

原始健保署 JSON 分檔不覆寫。`data/name-corrections.json` 保存每個健保碼的原中文／英文名、修正中文名、許可證、來源英文名、來源異動日、查核方法，以及官方 ZIP 的 SHA-256。網站與 SQLite 均套用相同校正，SQLite 的 `name_audit` 表可回查原文。名稱修正不會變更成分、含量、價格或三同比對資格，也不代表許可證目前有效；來源註銷狀態保留在校正證據中。

查核條件：依健保碼取許可證流水號，並區分製／輸家族；英文品名經全半形、大小寫及標點正規化後須相同。只移除明確的「鋁箔/膠箔」包裝尾註，另對一組製造商括號與成分括號對調的 Benamine 英文名做明確對應。多個候選中文名、英文實質差異、官方名稱仍含私人造字或缺字，一律不自動修正。新版本主檔原名稱或英文名與校正依據不符時，網站拒絕套用舊校正。

來源：https://data.gov.tw/dataset/9122 ，官方 ZIP：https://data.fda.gov.tw/data/opendata/export/36/json 。重建：`python3 scripts/verify_names.py TFDA_JSON.zip`，再執行 `npm test` 與 `python3 scripts/build_sqlite.py`。

### 在 GitHub 啟用

1. 建立儲存庫（例如 `santong-drug-search`），將本資料夾的內容放到 `main` 根目錄，含 `.github/workflows/pages.yml`。
2. 開啟 Settings → Pages → Build and deployment → Source，選 **GitHub Actions**。
3. 到 Actions 執行 `Test and deploy GitHub Pages`。成功後使用部署輸出的網址。
4. 若第一次部署因尚未設定 Pages 而失敗，完成第 2 步後重新執行。

上傳至公開儲存庫或 GitHub Pages 的藥品主檔可被他人讀取，不得放入病人、處方、帳號或其他非公開資料。

### 本機執行

需要 Node.js 24（測試、資料整理）及 Python 3（本機預覽）。

```sh
npm test
python3 -m http.server 8000
```

開啟 `http://localhost:8000`。請勿直接雙擊 HTML，瀏覽器可能阻擋資料載入。

### 正式資料準備

來源：中央健康保險署「健保用藥品項查詢項目檔」，政府資料開放授權條款第 1 版。

- 資料集與授權資訊：https://data.gov.tw/dataset/23715
- 官方查詢：https://info.nhi.gov.tw/INAE3000
- 查詢檔與格式說明：https://www.nhi.gov.tw/ch/lp-2466-1.html
- 處方替代條件：https://www.nhi.gov.tw/ch/cp-5798-d1af3-2844-1.html

官方公開摘要欄位不能直接保證完整複方含量、給藥基準及釋放型態，原始官方 CSV 不能直接用一般匯入按鈕載入。官方 TXT 已由 build_nhi.py 專用程式轉換。請由藥師依官方明細與許可證資料整理核對，轉成以下格式；不可把「規格量」直接視為每個成分含量，亦不可從藥名猜測。

`data/template.csv` 是欄位範本；`data/demo.json` 提供虛構格式例子。CSV 請使用 UTF-8；Excel 請另存 CSV UTF-8。每個健保碼保留一筆，對應同一價格有效期間；若需歷史資料，請另行建立主檔版本。本版拒絕重複健保碼，避免混用不同期間價格。

| 欄位 | 內容 |
| --- | --- |
| code | 唯一健保碼（必填文字） |
| name | 中文品名（必填） |
| englishName | 英文品名（可空） |
| ingredients | 完整成分陣列，每項有 name 與 strength，複方須列全；CSV 中使用 JSON 陣列字串 |
| form | 詳細劑型，含緩釋／腸溶等（必填） |
| specification | 給藥基準與必要規格，如每錠、每瓶 10 mL；含量應保留濃度基準（必填） |
| manufacturer | 廠商（可空） |
| price | 該給付期間健保支付價，數字；未知 JSON 用 null、CSV 留空 |
| validFrom / validTo | 價格給付有效起迄日，YYYY-MM-DD（必填，非許可證有效日） |

正式 JSON 可為陣列或 `{ "source": "來源", "updatedAt": "YYYY-MM-DD", "drugs": [...] }`。網站匯入只存於記憶體，重新整理後清除；不會自動寫入儲存庫。

管理者可將核對後的資料永久加入網站：

```sh
npm run import -- reviewed.csv "健保署主檔，藥師核對" 2026-10-30
npm test
git add data/drugs.json
git commit -m "Update reviewed drug master"
git push
```

更新日請填真實資料更新日。每次更新核對新增、停付、成分、價格及劑型，提交後 GitHub Actions 會重新部署。**本版沒有自動抓取或自動更新官方藥品資料。**

### 比對規則與使用界線

完整成分集合、各成分含量、詳細劑型及給藥規格經全半形、英文大小寫、連續空白正規化後，全部一致才列為候選；成分順序不同可匹配。沒有鹽類推論、單位換算、同義劑型合併或等效劑量建議，因此可能漏掉需專業判讀的候選。相同 ATC、相同主成分、名稱含相同字詞均不足以判定三同。資料正確性取決於主檔完整性；程式無法識別主檔是否漏填了某個成分。

清單會排除原品項。給付日期篩選僅依匯入有效期間，並非即時確認健保給付、供貨或庫存。支付價依資料標示之給付單位，非零售售價。程式未自動執行處方不可替代、支付價不高於原品項、給付規定、許可證、途徑、適應症或臨床等效性審核。須由藥師核對後決定，不可直接據此換藥。

### 驗證

`npm test` 驗證完整複方、劑量／鹽類／劑型／規格區別、給付日邊界、無效主檔拒絕、搜尋與 CSV 往返、試算表公式注入防護。部署前亦會執行。網站以文字節點呈現匯入欄位，避免把品名當 HTML 執行。
